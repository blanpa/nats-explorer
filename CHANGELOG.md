# Changelog

All notable changes to NATS Explorer. The format follows [Keep a Changelog](https://keepachangelog.com/); versions follow [SemVer](https://semver.org/).

## [Unreleased]

### Added
- **Explanations moved onto the controls they explain.** Every form field and checkbox carried its help text underneath, permanently, which turned the settings and the connection form into walls of prose that nobody reads twice. The text now sits behind a small mark next to the label and comes back on hover or keyboard focus -- 68 of them, plus the standalone paragraphs that described one control. It is hidden, not gone: it stays in the document for `aria-describedby`, so a screen reader reads it out as before.
- **A time range says how big it is, and fills itself in**: picking one used to load its first 2 000 messages and show that as the figure, which then climbed as you scrolled -- a number worth reading has to be right when it appears. The first request now asks the server for the range's total, counted from the index without touching a payload (0.45 s over 3 000 000 rows, a covering index scan), and the view keeps loading in the background until the range is in, up to 50 000 messages. Picking "24 h" over 32 794 recorded messages shows 32 794 straight away and has them all a moment later, with no scrolling. A payload filter leaves the total out rather than guessing at it: only reading the messages can say how many it keeps.
- **Four more ways to take messages out**, beside JSON and CSV: **NDJSON**, one message per line with a JSON payload as a document rather than a string, which is what `jq`, DuckDB's `read_json_auto()`, ClickHouse and BigQuery read without a second parse; **CSV with one column per field**, spreading the payload into `payload.<path>` and the headers into `header.<name>`, so an export is usable in a spreadsheet or pandas without unpacking anything first; **payloads only**, the bodies and nothing else; and a **replay script** for the `nats` CLI, which quotes for the shell, carries the headers, sends binary payloads through base64 and stdin, and escapes `{{` as `{{"{{"}}` because `nats pub` expands Go templates in the body -- a payload holding `{{Count}}` would otherwise be published as `1`. Verified against the real CLI, binary included.
- **Several fields in one chart, or one chart each**: clicking a second number adds it to the chart instead of replacing the first, up to six. Separate charts is the default -- each field keeps its own axis, which is the only honest way to put a temperature next to a counter -- and "One chart" overlays them to compare shapes. Overlaid, fields with different units are scaled to their own range and the axis reads in per cent, while the values above the chart stay the ones the messages carried: an axis that is meaningless as a number must not also show meaningless numbers. Each field has a colour, in the legend and in the chips above.
- **The chart says how it reduced the data, and lets you choose** (`agg=` on `/api/history/series` and `/api/streams/{name}/series`): min/max (both extremes of a bucket, the default and the only one that never hides an outlier), average, minimum, maximum, sum, count of messages carrying the field, and rate per second. Rate is what makes a counter readable -- parts produced, kWh, bytes are staircases whose raw value says nothing, and their slope is the number anyone wanted. A decrease reads as no change, so a restarted counter does not put one enormous negative spike through the chart. The reduction applies to the minute aggregates over long ranges too, so a chart does not quietly change meaning when the range grows past six hours.
- **Messages can be kept forever**: the retention offers "Forever (never delete)" beside the durations (`HISTORY_RETENTION=0`), and the cleanup then deletes nothing. It was capped at a year, so a recording meant to be permanent had to be renewed by hand. The hint under the field says what it means -- the file grows until the disk is full -- because it is the one setting here that waiting cannot undo. The range picker gained a `30 d` and an `All` preset: with no retention there is no sensible preset to stop at, and reaching further back used to mean typing a start date.
- **What is written to disk can be narrowed**: "Only write messages matching" in the history setting (or `HISTORY_FILTER`) takes a CEL expression over the same variables as a payload filter, and only what it accepts is persisted. It is evaluated before the queue rather than in the writer, so what it excludes never takes up buffer and a burst of uninteresting subjects cannot push out the ones being kept. The live feed and the subject tree are never filtered -- they describe what arrived -- and what the filter left out is counted apart from what was lost. Filter variables are resolved lazily now, so an expression over the subject costs about 250 ns per message instead of the 3.1 µs parsing every payload up front took.
- **The write buffer is a setting** (`HISTORY_QUEUE_BYTES`, 16 MB to 1 GB, 64 MB by default): how much of a burst is held in memory while the disk catches up. It was fixed at 64 MB with no way to raise it.
- **Messages that did not reach the disk are named, not only coloured**: the status bar shows the count itself rather than turning a size amber, and the setting behind it lists what to change, cheapest first -- narrow what is written, switch the full-text index off, raise the buffer -- leaving out the ones already in place. The counter alone said something had gone wrong without saying what to do about it, and it does not say which part is affected: the live view has no gaps, only the copy on disk.
- **A consumer can be paused**: the pause button in the consumer list stops delivery for five minutes and shows how much of it is left; the play button resumes it early (`POST /api/streams/{stream}/consumers/{name}/pause` and `/resume`). A pause has a deadline the server keeps, so a consumer swapped out or a backlog drained by hand cannot stay silent because someone forgot it.
- **The stream form carries the NATS 2.11 limits**: `discard new per subject` applies the new-discard policy per subject instead of to the whole stream, `allow per-message TTL` lets publishers expire their own messages with a `Nats-TTL` header, and a subject delete marker gets its own lifetime.
- **TLS before the server's INFO**: a connection can negotiate TLS first, for servers configured with `handshake_first`. Without it such a connection hung until the timeout with nothing to say why.
- **The server runs under a reverse-proxy subpath**: `BASE_PATH=/nats` mounts every route under the prefix and writes it into the page as `<base href>`, so the UI builds its API, websocket and asset URLs from `document.baseURI`. One build serves both `/` and any prefix, and the proxy forwards the path as it is -- no rewrite rule.
- **A Helm chart** in `deploy/helm/nats-explorer`: deployment, service, optional PVC for the connections and the recorded history, optional ingress whose path becomes `BASE_PATH`, and the auth token as a secret.
- **The subject tree shows figures, not payloads**: a branch carries the messages of its subtree and how many subjects with messages are under it (`sc` on a tree entry), a leaf its messages and rate. The payload preview is off by default and switched on with the quote icon in the tree header; off, the `view` command carries `noPreview` and the server leaves the payload out of the feed entirely -- it was the largest part of every entry.
- **Schema validation**: the derived schema can be pinned as the expected one ("Pin as expected" in the schema panel, `PUT /api/schemas` per subject pattern). From then on the payload filter carries the verdict: `valid` and `violations` are CEL variables, so `!valid` narrows the subject tree, the history, a time range and the search to the messages that do not match -- and is a complete alert rule, without the alerts engine knowing what a schema is. The panel counts how many of the sampled messages fail ("2 of 43 do not match") and jumps to them; the publish form warns before sending a payload that would not match (`POST /api/schemas/check`). Types and required fields are enforced, observed ranges are not: a range from samples is not a rule, and unknown fields only count when the schema was pinned strict.
- **A payload filter now narrows an open subject** instead of only adding to it: the answer to a filtered history request replaces the message list. Setting a filter while a subject was open used to leave the list as it was.
- **The subject tree survives a restart**: with the history on disk, connecting restores the recorded subjects and their message counts into the tree before a single new message arrives, for the subjects the current subscriptions cover. Until now a restart showed an empty tree until every subject sent again, which on a namespace where some subjects report once an hour took an hour. Rates and payload previews stay empty: they describe the live connection and fill in with the next message.
- **The derived schema can be copied out**: "Copy as" in the schema panel writes a JSON Schema (draft 2020-12) or a TypeScript interface to the clipboard, rebuilt from the flat field paths with nesting, arrays, optional fields and enumerations. Observed ranges and presence become descriptions rather than constraints, and both carry a header saying they were derived from samples.
- **The history rail is resizable**: drag the edge between the rail and the message, double-click resets it. The width is remembered like the explorer's. The drag handle is now a shared component with the pane's bounds as props.
- **Every message list loads as it is scrolled**, not just the history rail: the list below a branch, the search results and the merged list of several watched subjects page backwards too. The branch and the search merge every subject under a node, so each carries its own cursor -- `branchBefore` on `GET /api/history` with a `branchMore` beside it, `beforeTs`/`beforeSeq` with `more` on `/api/history/search`. In memory the cursor is the arrival sequence, which orders that merge because it is arrival order within a connection; the database orders by `(timestamp, sequence)` and pages on both.
- **The history rail pages backwards**: it pages backwards instead of stopping at the messages of the first request -- 500 at a time from what the server holds in memory (up to 10 000 per subject), 2 000 at a time from the persistent copy in a time range. `GET /api/history` reports `more` next to the messages, so a payload filter emptying a page no longer looks like the end, and `GET /api/history/range` takes a `beforeTs`/`beforeSeq` cursor. The cursors are per connection, because sequences are.
- **The persistent history is a setting**: a gear in the rail opens the settings, where the SQLite copy of the history is switched on or off, gets its retention, and can be deleted from disk (`GET`/`PUT /api/history/persistence`). The database is opened and closed while the server runs, so nothing has to be restarted. `HISTORY_DB` still wins: an installation configured by its environment reports the setting as managed and refuses to change it. The history figures in the status bar open the setting.

### Fixed
- Removing a subscription took everything it had collected out of the subject tree, the counters and the in-memory history. Narrowing the patterns therefore erased the view of what had already arrived -- and with `>` now removable, that meant emptying the tree. Nothing is forgotten on a subscription change any more: the tree is what the connection has received, not what it is listening to at this instant. An unsubscribed subject stops growing, its rate falls to zero, and its messages stay readable. Emptying the tree is its own action, and asks first.
- The `>` subscription could not be removed. Five layers put it back when the list ran empty -- the panel, the saved connection, the change endpoint, the subscription manager and the status -- so the unsubscribe button did nothing at all. It is the one subscription nobody can afford on a busy cluster, and it was the only one that could not be dropped. A connection with no subscriptions is a state in its own right now: it receives nothing, says so where the count used to be, and patterns can be added again afterwards. Opening a connection without naming any still subscribes to `>`.
- Branches could not be collapsed while a subject filter was on. Filtering shows every match, which is right -- typing a filter and seeing nothing but roots would be useless -- but it was written as "everything is expanded", so the chevrons and the collapse-all button did nothing. Open by default is not the same as unclosable: a branch closed under a filter now stays closed, without disturbing what was open before the filter and without outliving it.
- The Size column of a message list could not be resized sensibly. Its grip sat on its right edge, which is the table's own edge and cannot move: dragging right widened the column leftwards, so the line under the pointer stayed put while the boundary on the other side moved. The grip also sat two pixels from the edge, under where a scrollbar appears. It is on the left edge now -- the boundary that actually moves -- pulling it left widens the column, and the grip reaches above and below the header row so there is something to aim at.
- An export wrote what had been scrolled into view, not what was selected. Picking a time range and exporting gave the first page of it: "All" over a subject with 27 000 recorded messages produced a file with 4 000, and nothing said so. With a range active the export now pages the rest in first and the menu says what it covers ("Everything in the last 30 d") instead of a count that was only the loaded part. It stops at 200 000 messages and says the file is short rather than writing half of one.
- The message count beside a branch reported the live list while a time range was active: it read "200 recent messages below this subject" next to a view showing 2 000 of them. It counts what is on screen, and names the range it belongs to.
- The CSV export dropped the message headers, which the JSON export kept. They are a column now.
- The buttons beside an open subject sat in no order: the eraser, the one irreversible action of the row, was second of six, one slot from where the pointer lands, while the two controls that both describe the subject -- bookmark and copy -- were first and fifth with three unrelated things between them. They are three groups now, in the order the questions come: what is this subject (bookmark, copy), what is in it (search, export), what do I do with it (publish). Clearing the history moved into an overflow menu beside them: a row where every other click is harmless is the wrong place for a button that deletes from disk.
- The eraser in the subject tree cleared the whole history whatever was selected, so clearing one branch took unrelated ones with it -- the only clear that was scoped sat unlabelled in the detail header, where it was easy to miss. With a subject selected the dialog now asks which: only that subject and everything below it, or everything. The narrow one is what Enter takes.
- "Clear message history" left the subject tree standing, with every subject and its count, while the messages behind them were gone -- and the persisted copy was not touched at all, so the next connect restored the tree from disk and the clear looked like it had done nothing. It now empties the tree, the per-subject counters and the stored messages of every connection (or of one with `connId`), and asks first. Subjects come back as they send again.
- A tree restored from the persistent history showed subjects with a message count but no value: the newest message was not restored with them, so the preview stayed empty and the payload filter could not judge those subjects at all -- with a filter active they simply dropped out of the tree. The restore now brings the newest message back with the count, whole rather than truncated, because the filter evaluates against it. Payloads over 4 KB are still restored as a count only.
- The websocket endpoint was built from a value the bundler could fold away, which under a subpath sent it to the wrong path while the REST calls were still right. The prefix is read on every call now.
- The desktop app lost its message history on every restart. It never opened a database -- the only way to ask for one was `HISTORY_DB`, which a packaged app has no way to set. It now keeps the history in `history.db` next to the settings by default, and the setting above switches it off.

## [0.3.0] - 2026-09-08

### Added
- **Clear the history of one subject**: the eraser in the subject header forgets what was recorded for that subject, or for a branch and everything below it (`DELETE /api/history?subject=&branch=1`). Memory and the persistent copy including the minute aggregates are cleared, and the subject leaves the tree until the next message arrives.
- **A chart point opens its message, and the message is marked in the chart**: clicking a point pins the message behind it in the payload viewer, chosen by value and not only by time, so a peak in a downsampled or per-minute series opens the message that caused it; points the browser no longer holds are read from the persistent history. The message on screen is marked on the curve, with its value and time in the chart header.
- **Support bundle**: `GET /api/bundle` writes a zip with the recorded messages of a range, the server snapshot, the streams with their consumers and the KV buckets; `POST /api/bundle/import` opens such a file as a read-only connection that every module reads like a live one (`GET /api/bundle/{id}` for the manifest, `DELETE` to close it). In the UI: the package icon in the monitoring header, the export menu of a subject, and "Open support bundle" in the connection switcher.
- **Search across all subjects**, with a full-text index: `GET /api/history/search` no longer needs a subject, and with `HISTORY_DB` an FTS5 index answers word and prefix queries; a fragment falls back to a scan. The results line carries the scope toggle.
- **Minute aggregates for long ranges**: the history writer keeps minimum, maximum, sum and count per subject, numeric field and minute, so a chart over days is a few hundred points (`source: "rollup"` on `GET /api/history/series`, field list at `GET /api/history/fields`, retention via `ROLLUP_RETENTION`, default 90 days).
- **Audit log**: every write under `/api` is recorded with user, role, object, source address and status (`GET /api/audit`, admin only), stored next to the settings or in memory. Refused writes are logged too; reads are not.
- **Consumer lag over time**: consumers carry a lag column with a trend marker, and an expanded row charts pending and ack-pending from samples taken on every refresh.
- **Alerts and silent subjects**: rules watch a subject pattern for a CEL expression that holds or for a subject that stopped sending, with severities, an optional webhook and a dry run against the recorded messages. The backend evaluates them on the message path, so they keep working without an open browser; the new Alerts module shows what is firing, the rules and a log, and the rail badge counts active alerts.
- **Derived schema per subject**: the subject detail shows the fields of a subject's JSON payloads with types, presence, ranges, enumerations and examples, read from the recorded messages (`GET /api/schema`), and marks schema drift when the newer messages differ from the older ones.
- **Bookmarks for subjects**: a star keeps a subject with a name, group and note; the bookmarks panel above the tree gets back to it even when it is filtered out, and the note shows under the subject header.
- **Response-time histogram**: a repeated run reports p99 next to p50 and p95 and draws where the replies landed, so a bimodal distribution is visible instead of averaged away.
- **Stream replication**: a stream's mirror and sources are reported with their lag and last activity, and every stream says which other streams mirror or source from it (`mirror`, `sources`, `sourcedBy` in the stream info).
- **Payload filter (CEL)**: an expression like `payload.temp > 80 && subject.endsWith(".temp")` narrows the subject tree to subjects whose last message matches, and the same `expr` parameter filters `GET /api/history`, `/history/search`, `/history/range` and `/history/series`. Expressions see `subject`, `payload`, `raw`, `kind`, `headers`, `size`, `timestamp` and `reply`; they are compiled once and evaluated only for what a tab looks at. A compile error is reported to the tab instead of an empty tree.
- **Accounts and roles**: `AUTH_USERS` names a file of `name:role:bcrypt-hash` lines (`nats-explorer hash-password` prints a hash); the UI shows a login, admins may change things, viewers get a read-only explorer (write actions hidden, backend answers `403`). Logins set an HttpOnly session cookie that also carries the websocket, so no token sits in a URL or in browser storage; `AUTH_TOKEN` uses the same cookie after the token is entered once. Scripts and scrapers keep bearer or basic auth (`POST /api/login`, `POST /api/logout`, `GET /api/auth`).
- **`GET /metrics`**: the explorer's own counters in the Prometheus text format (messages received, throttled and per second per connection, distinct subjects, history size in memory and on disk, websocket clients, connection states).
- **Auto-connect**: with `STORAGE_DIR` a saved connection can be marked "Connect when the server starts"; the backend opens it itself, so history and metrics collect without a browser.
- **Payload decoders**: rules per subject pattern decode MessagePack, Protocol Buffers (pasted `.proto` and message type) or Avro (pasted schema) into the JSON tree, with a "Decoded" view in the payload viewer; the rules are kept with the other settings. The libraries load on first use.
- **Client tests**: component tests with Testing Library and jsdom (login dialog, subscriptions panel, trend strip, payload viewer) and a unit test for the feed worker's tree and feed logic, which moved into `worker/feedCore.ts`.
- **Persistent history**: `HISTORY_DB` keeps a SQLite copy of every message with `HISTORY_RETENTION` (default 72h); the subject detail gets a range picker, and `/api/history/range`, `/search` and `/series` accept `from`/`to`. The Docker Compose file mounts a volume for it.
- **Search, export, replay**: search the recorded history of a subject or branch by subject or payload text (`GET /api/history/search`); export loaded messages as JSON or CSV; replay them through the publish API with a pause and an optional subject prefix rewrite. Available in the subject detail, the multi-subject view and the stream message table.
- **Streams**: jump to a point in time (`GET /api/streams/{name}/seq?time=`); consumers can be edited after creation (`PUT /api/streams/{stream}/consumers/{name}`: description, ack wait, max deliver, max ack pending, filter subject).
- **Watch several subjects at once**: Ctrl/Cmd-click in the tree adds subjects to the selection; the detail pane shows the latest value and rate of each and a merged, newest-first list of their messages. The `focus` websocket command takes a list of subjects.
- **Live subscriptions**: the Subjects pane lists what a connected server is subscribed to, one row per pattern with the subjects it matches and its rate (new `patterns` in the `stats` event), with a field to add patterns, an X to unsubscribe and toggles for the system subjects. Every change applies without reconnecting (`PUT /api/connections/{connId}/subscriptions`) and is remembered in the saved connection. The fields left the connection dialog.
- The demo scripts in `dev/` take the server from `NATS_URL`.
- **Resizable columns** in the branch and multi-subject message lists: drag the grips between the headers, double-click resets, widths are remembered.
- **Subject detail shows more at once**: the history rail is open by default and the numeric fields of the latest message appear as sparklines with their current value; clicking one opens the full chart. The stream message table fits the viewport (fixed columns, subjects keep their last segments readable, actions stay visible). The subscriptions panel starts collapsed while everything is subscribed and shows its patterns in the header. The Requests module offers "New request" in its empty state. Keyboard: `/` focuses the filter, Escape clears it, `j`/`k` move through the subject tree.
- **UI polish**: empty states and form hints say one thing; server IDs are abbreviated with the full value in the tooltip and the stream placement column only appears with more than one server; one number format (`1,234`) in charts, headers and footer regardless of the browser locale; the monitoring module shows one line instead of six placeholder charts until samples exist; stronger borders and selection in the light theme.
- **Code structure**: the monitoring dashboard, stream message table and cluster overview are split into focused files (charts, tables, toolbar, rows); the message list, payload tone colours and message identity helpers are shared modules; the subject detail, KV bucket view and connection dialog are split into focused components; websocket events are typed structs on the Go side; the e2e suite is one file per module with shared support; the review document is a decision list.
- **Frontend stack**: React 19, Zustand 5, Tailwind 4 (Vite plugin, theme in `index.css` instead of `tailwind.config.ts`, no PostCSS), lucide-react 1, tailwind-merge 3. Screens compared module by module before and after, no visual changes.
- **Toolchain**: Vite 8, Vitest 5, TypeScript 7 and `@vitejs/plugin-react` 6 (client typecheck 2.6 s → 0.4 s, production build 5.0 s → 0.6 s on the same machine); Biome for linting and formatting (`bun run lint`, `bun run format`, checked in CI); the unused root `esbuild` dependency is gone.
- **Bun** replaces pnpm and Node.js as package manager and script runner (`bun install`, `bun run …`, `bun.lock`); the Docker image builds the UI on `oven/bun`, CI and release use `oven-sh/setup-bun`. The demo scripts run on the Bun runtime.

- **Charts for streams**: a number in an opened stream message charts that field over the last 500 to 50 000 messages of the stream, per subject or across all, with live refresh while tailing (`GET /api/streams/{name}/series`).
- **Charts over the whole history**: `GET /api/history/series` extracts a numeric field over up to 10 000 recorded messages per subject and downsamples it to min/max buckets; the chart appends live values.

### Fixed
- **Broken links on the documentation site.** Every `{% link %}` on the site rendered without the `/nats-explorer` base path, so "Install", "Features", "Deployment", "Architecture", "Development" and "License" led to a 404 from the home page, the deployment page and the settings table. The 404 page itself was a `.html` file holding Markdown, so it showed its own source instead of a list of links. And `{{i}}`, `{{ts}}`, `{{uuid}}` and `{{rand:MIN-MAX}}` -- the request runner's placeholders -- were evaluated as Liquid and rendered as nothing, which left the sentence about them meaningless in both the features and the architecture page.
- **Data race when the subscriptions changed.** Swapping the subscribed patterns on a running connection replaced the pattern list under the manager lock while the shard workers read it under their own; `go test -race` caught it. The list is now an atomic snapshot that is replaced, never edited, so the hot path reads it without a lock.
- **The cluster test talked to the developer's own NATS.** Without system credentials the overview falls back to HTTP monitoring, and the test left the port at the default 8222, so it reached whatever server happened to run there instead of the embedded one. It now pins the port to the embedded server's client port.
- **The Services module went blank without any service.** NATS answers a discovery request that nobody responds to with an empty status message; it ended up in the list as `null` and crashed the page. Status replies are dropped in the backend now, and the store ignores entries that carry no service, so the module shows its empty state as intended.
- **Changing subscriptions no longer clears everything.** Adding a pattern used to stop and restart the connection's subscription manager, which threw away the subject tree, the counters and the recorded history of every pattern. A change now swaps the subscriptions in place and forgets only the subjects that no pattern covers any more; the persistent history keeps them regardless. Counters of a pattern that stays are kept too.

### Changed
- **New screenshots**, taken against a running plant simulation instead of a half-empty test server: the subject tree unfolded down an ISA-95 path with rates per branch and a chart of the field that was clicked, a stream with its limits and placement, seven alert rules with three firing and a log that has resolved entries in it, the monitoring dashboard with its six throughput curves, 400 requests with p50/p95/p99 and a visibly bimodal histogram, a Key-Value bucket with a key and its revisions, and the connection switcher over a populated window. Two of them are new (requests, Key-Value), all seven are on the documentation site as well as in the README, and the set is 40 % smaller than the five it replaces.
- **The documentation site was rebuilt.** [blanpa.github.io/nats-explorer](https://blanpa.github.io/nats-explorer/) has a landing page with the download table and the screenshots that so far only the README showed, a page per audience in a sensible order, a table of contents on the two long pages, search over headings, "Edit this page on GitHub" under every page, a 404 page that points somewhere, a favicon and a license page that says in a table what the AGPL means for a reader. The architecture overview is a Mermaid diagram instead of ASCII art, and its component list matches the code again -- it still named folders that no longer exist, missed five that do, and credited a charting library that was never a dependency. `scripts/check-docs.sh` checks front matter, every `{% link %}` target, every image and every anchor, and CI runs it together with the real Pages build, so a broken link fails on the pull request instead of on the deployment.
- **The UI offers its source.** The status bar carries a quiet link with the version and the word `source` at its right end, and the login dialog carries it too, so it is reachable before anyone signs in. It leads to the source of the running build: `GET /api/app` now returns `commit` and a resolved `source`, the build scripts stamp the short commit next to the version, and the link becomes the tree at that commit -- or the release tag when only a version is stamped. A deployment of a modified version points `SOURCE_URL` (or a stamped `-X main.defaultSource=…`) at its own repository, which is what the AGPL asks of software people reach over a network. In the desktop app the link opens the system browser instead of navigating the webview away from the app.
- **Licensed under the AGPL v3.0 or later** (previously Apache 2.0). Using, self-hosting and modifying the program stays free; a modified version that is distributed or offered over a network has to hand its users the source under the same license, so a closed hosted fork is not possible. The project name and marks stay outside the license, so a fork has to carry its own name.
- **The server shuts down.** `createServer` returns a handler that can be closed, and closing it stops the subscription workers of every connection, disconnects from NATS, stops the alert engine and closes the persistent history. The binary does it on SIGINT/SIGTERM after draining the listener, so the last batch of the history is written instead of killed mid-write; the desktop app does it when the window closes, and every test case does it through one helper. A goroutine test covers it: without the shutdown a single server leaves about twenty goroutines behind.
- **Repository cleaned up.** `go.mod` lost two dependencies an unfinished OIDC attempt had left behind, and CI now fails on an untidy `go.mod`; two unreachable Go functions and three unused client helpers are gone; five ESLint suppressions from before the move to Biome were replaced by Biome ignores with a reason, so `bun run lint` is free of warnings again; `.env.example` lists all twelve settings the server reads, the documentation site carries the features added since 0.2.0, the standalone compose file runs the released image with a volume for the history instead of building from source, and all seven screenshots were retaken against neutral demo traffic (orders, sensors, services, a config store and a pricing service) instead of the factory simulation, at the same file size as before.
- **Permanent download links.** A release now attaches every package a second time under a name without the version, so `releases/latest/download/nats-explorer-desktop-windows-x64-setup.exe` and its siblings always hand out the current build. The README and the installation guide link to them directly, and `SHA256SUMS.txt` covers both names. The copies were added to v0.2.0 as well, so the links work from today.
- **Jumping to a subject unfolds the tree to it.** "Open subject" in a message panel, a row of a message list, a bookmark and an active alert now open the branches above the subject and scroll it into view, instead of selecting something the tree does not show.
- **A row in a message list opens its payload.** Search hits, the messages below a branch and the merged list of several subjects showed only a preview and jumped to the subject on click. A click now shows the message under the list, with "Open subject" for the jump.
- **A time range now looks like the live view.** Picking a range used to switch the subject detail to a plain message table. It keeps the same layout instead, with the history rail, the payload viewer, the trend sparklines, the chart and the schema, all reading the messages of that period; the schema follows the range as well.
- **Hot path rebuilt for throughput**: messages are kept as the bytes nats.go delivered and classified only when shown; counters and the history are sharded by subject with one worker per shard, the tree learns about changes at tick time; per-subject rates are ten second buckets instead of timestamp lists; the history uses ring buffers; deliveries travel in batches. At 400 000 msg/s the backend went from 125 % to 83 % of one core, at 100 000 from 29 % to 25 %; `PPROF=1` serves Go's profiler.
- **Server-side subject tree**: the backend keeps the hierarchy with subtree totals and sends a tab only the nodes its view shows (expanded branches, or the paths of filter matches; new `view` websocket command). The filter runs on the server over the whole namespace. Collapsed branches cost nothing; with the default view the tree feed under 5 000 subjects at 20 000 msg/s dropped from 1.2 MB/s to about 10 KB/s.
- **Feed worker and MessagePack**: the websocket moved into a web worker that decodes frames, keeps the tree and coalesces the feed; the main thread only renders. Frames are MessagePack (`?enc=msgpack`, about 20 % smaller than JSON for the tree feed; `ne.wire = "json"` in local storage switches back). With the tree fully expanded under the stress load the main thread went from 9 % to 4 % busy without a single long task.
- The Go process gets a soft memory limit of twice `HISTORY_MB` plus 128 MB.
- **Pull model for the live feed**: the backend records every message in a bounded in-memory history (`HISTORY_MB`, default 256 MB, 1000 messages per subject; new `GET/DELETE /api/history`) and a browser tab only receives the messages of the subject or branch it looks at (up to 50 msg/s per subject and 2000 msg/s per tab). The history of a selection is fetched on click and merged with the feed by sequence number. Traffic and browser memory now scale with what is on screen: under 5 000 subjects at 20 000 msg/s the JS heap went from 48 MB to 16 MB, browser main-thread time from 17 % to 9 %, socket traffic from 1.8 MB/s to 1.2 MB/s.
- Subject tree deltas are applied to the tree in place instead of rebuilding it; store updates from the feed are coalesced per animation frame; the history and branch lists are virtualized; the counters in the status bar come from a `stats` event once a second.

## [0.2.0] - 2026-09-06

Licensed under the Apache License 2.0 from this release on (previously MIT).

The first release that ships as an installable desktop application. Everything below was reviewed and verified against real NATS setups: a mutual-TLS server, a three-node cluster with a leaf node and JetStream domains, and a 20 000 msg/s stress load.

### Added
- **Desktop app** for Windows (per-user NSIS installer and portable zip), macOS (universal `.dmg`) and Linux (AppImage, `.deb`, tar.gz), built by the release workflow and smoke-tested on every platform runner.
- **Persistent settings** for the desktop app and for servers started with `STORAGE_DIR`: connections, request templates and preferences live in `settings.json` in the OS config directory; credentials go to the system keyring (Secret Service, Keychain, Credential Manager) or a user-only `secrets.json`.
- **Requests module**: Postman-style request templates in the sidebar with import/export, repeated runs (up to 10 000 sends, parallel senders, interval) with throughput and latency percentiles, and `{{i}}`, `{{ts}}`, `{{uuid}}`, `{{rand:MIN-MAX}}` variables. New `POST /api/run`.
- **Cluster module**: every server of the cluster, the JetStream meta cluster and stream placement via system-account credentials (`$SYS.REQ.SERVER.PING.*`), with a single-node fallback. New `GET /api/cluster/{connId}/overview`.
- **Monitoring history**: messages/s and bytes/s in and out, JetStream API rate, connections, subscriptions and CPU over time; cluster route and leaf node tables with traffic (`leafz`).
- **JetStream domains**: `jsDomain` / `jsApiPrefix` per connection, per-call `?domain=` override and a domain switch in the JetStream, KV and Object Store panes.
- **TLS with certificates**: CA, client certificate and key per connection (files or paste), insecure mode for test setups.
- **Value chart types**: line, area, step, bars, dots.
- Live KV watch and stream tail over the websocket, optional API token (`AUTH_TOKEN`), branch view for subject groups, saved recent sends, direct object download.
- Test coverage: Go unit and embedded-server end-to-end tests, Vitest, Playwright smoke suite, desktop smoke tests; CI builds and smoke-tests the Linux desktop app on every push.

### Changed
- **Live feed protocol**: the subject tree is sent as flat, delta-only entries with payload previews instead of full nested trees; focused subjects get their own budget, the rest share a background budget; websocket compression. Under the stress load this cut browser main-thread time from 62 % to 11 % and traffic from about 30 MB/s to about 150 KB/s.
- **UI redesign**: calmer visual language (figure strips instead of tiles, plain empty states, quiet destructive actions, no success toasts), system subjects and KV/Object backing streams hidden by default, module switches served from a result cache.
- Dependencies: Go 1.26, nats.go 1.53, nats-server 2.14 (tests and Docker image), Wails 2.11.

### Fixed
- Desktop app lost saved connections on every start (local storage was bound to a random port).
- Desktop window showed a Wails error page instead of the UI with Wails 2.11.
- "Not connected" flashed before the backend had reported its connections.
- Numerous smaller issues found in the review: throttled counters, tree memoisation, StrictMode double sockets, Docker build with pnpm 11, label/input linking in dialogs.
