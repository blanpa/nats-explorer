# Code review and redesign, September 2026

This document lists what the review found in the previous code base and what
was changed. Line references point at the old files.

## Bugs that broke features

| Area | Finding | Fix |
|---|---|---|
| KV edit / put | Client sent `PUT /kv/{bucket}/{key}`, server only registered `POST` → every save failed with 405. | Server accepts `PUT` and `POST`. |
| Object upload | Client used `PUT`, server `POST` → uploads impossible. Body was base64 inside JSON (3× memory). | `PUT`/`POST` both work; the browser now streams the raw file body. |
| Stream message delete | Client called `/streams/{s}/messages/{seq}`, server had `/streams/{s}/{seq}`. | Route is `/streams/{name}/messages/{seq}`. |
| JWT auth | `nats.UserCredentials(cfg.Creds)` expects a *file path*; the UI sends the file *content*. Never worked. | `nats.UserCredentialBytes`. |
| Binary payloads | Raw bytes were put into a JSON string; Go replaced invalid UTF‑8 with U+FFFD and the hex view called `atob()` on it, which threw and blanked the page. | Binary payloads are base64 on the wire; hex view decodes correctly, text uses `TextEncoder`. |
| Server info | UI read `host`, `port`, `jetstream`, `tlsRequired` that the API never returned → “undefined:undefined”, JetStream always “Disabled”. | New `/api/server/{connId}` returns address, TLS, RTT, JetStream probe with account limits and client stats. |
| Tree expand/collapse | Toggling only worked while messages were flowing: the expanded set lived in a ref and a “re-render” was forced via `setSelectedSubject(sameValue)`, which zustand ignores. | Expanded paths are real store state. |
| Websocket hub | The reader goroutine closed `send` while `Broadcast` could still write to it → “send on closed channel” panic under load/disconnect. No ping/pong, dead tabs lingered. | Writer/reader use a `done` channel, channel is never closed, ping/pong with deadlines. |
| Service discovery | Replies were appended from the NATS callback without a mutex and read while still being written (data race); handler slept 2 s. | Mutex, context‑aware wait (1.2 s default, `?waitMs=`). |
| Reconnect state | NATS disconnect/reconnect events never reached the UI; the status stayed “connected”. | Disconnect/Reconnect/Closed handlers push status (`reconnecting`, `lastError`, `reconnects`). |
| Stale connection id | After a disconnect `activeConnId` kept pointing at the removed connection; JetStream/KV calls then failed with “not connected”. | Store validates the active id and cleans trees/messages of vanished connections. |
| Saved ↔ live matching | Saved connections were matched to live ones **by name**; two entries with the same name collided. | Saved entries have a stable id which is sent to `/connect`. |
| Dev double socket | In StrictMode the effect cleanup closed the socket, its `onclose` scheduled a reconnect, and the re-run opened another → two sockets, every message counted twice. | Manual disconnect suppresses reconnect and detaches handlers. |
| Monitoring URL | Derived with a regex that broke on `nats://user:pass@host`, `tls://` and picked `natsPort + 4000`. | `url.Parse`, default port 8222, explicit URL wins. |
| Store lock | `nats.Connect` ran while holding the store mutex → every other API call blocked for the whole dial timeout. | Dial outside the lock. |
| Chart | `preserveAspectRatio="none"` stretched the axis text; memo never updated because the message array is mutated in place. | Width from `ResizeObserver`, per‑batch array copy. |

## Code quality

- Two design systems fought each other: custom `.mqtt-*` classes plus a
  hand‑written “Tailwind compat” layer that re-implemented `bg-card`,
  `text-muted-foreground` … because the Tailwind config expected HSL triplets
  while the CSS defined hex values. Replaced by one token set (RGB triplets)
  that Tailwind consumes directly.
- `shared/` types existed but nothing imported them; the client redefined the
  same interfaces and used `any` almost everywhere. The client now depends on
  `shared` and the types describe the real API.
- Detail panes talked to lists through `useStore.setState({ _selectedStream } as any)`
  and `useStore.subscribe`. Selections are typed store fields.
- `alert()` / `confirm()` for every error and destructive action → toasts and a
  confirm dialog.
- Dead code: `MessageList`, `MessageDetail`, `header-conn-pill` CSS, the first
  `BuildTree` in `tree.go` (looped over everything, then called the real
  implementation), duplicated `GetStatus`/`GetStatusLocked`, unused Radix
  packages, committed `tsconfig.tsbuildinfo`.
- Whole‑store subscriptions (`const { … } = useStore()`) in Header, StatusBar,
  Sidebar and MessageView re-rendered on every message batch. Selectors now.
- Company‑specific presets (`uns.>`, `events.>`) in the connect dialog removed.

## Security notes (unchanged behaviour, now visible)

- Credentials are stored **unencrypted** in `localStorage` and sent to the
  backend on connect. The dialog says so. Do not expose the backend port beyond
  localhost/trusted networks; there is no authentication on the API.
- The websocket origin check now only accepts same‑host or loopback origins
  (was: everything). CORS with `*` + credentials was removed; the UI is always
  served from the same origin.

## Redesign

- Icon rail for the seven modules, a resizable explorer pane, a detail pane,
  header with connection switcher and live rate, compact status bar.
- One connections dialog (list + form) instead of an inline editor and a
  separate “advanced” dialog with different field sets.
- Subject tree: virtualized, keyboard navigation (arrows, Home/End, Enter),
  expand/collapse all, guide lines, per-connection dots when several servers
  are connected, throttle counter in the status bar.
- Subject detail: pinned/live indicator, history side list, LCS line diff,
  responsive chart with hover, headers, “publish here” prefill.
- JetStream: create **and edit** streams (all limits, flags, humanized max‑age),
  messages page from the newest sequence backwards with paging and jump‑to‑seq,
  inline payload/headers, consumer table with create dialog and details.
- KV: key filter, edit with revision feedback, purge, full history table.
- Object store: drag & drop upload, streamed download, digest column, delete store.
- Services: grouped instances, endpoint stats, jump to publish for an endpoint.
- Monitoring: stat tiles, JetStream usage bars, routes, connections sorted by
  traffic, refresh interval control, actionable error when the HTTP port is
  not reachable.
- Light and dark theme from one token set, follows the OS preference on first run.

## Second pass (same day)

- **Tests.** Go: unit tests for the tree builder, payload encoding, monitoring
  URL derivation, token middleware, connection store, and the websocket hub
  (broadcast during disconnect, slow clients), plus an end‑to‑end test that
  boots an embedded `nats-server` and exercises connect, stream paging, KV,
  object store, the live websocket watches and auth. Client: vitest for
  `diff.ts`, `utils.ts`, `tree.ts` and saved‑connection migration. E2E: a
  Playwright smoke suite in `e2e/` that runs in CI against a NATS container.
- **Stream paging** uses an ephemeral ordered consumer (one round trip per
  page) with a per‑sequence fallback.
- **Live updates.** The websocket now accepts client commands; KV buckets are
  watched server‑side and stream views have a live tail.
- **Optional API token** (`AUTH_TOKEN`) with a one‑time prompt in the UI.
- Smaller: branch selection shows recent messages of the whole subtree,
  collapsed branches show their aggregated rate, the publish panel remembers
  recent sends, object downloads stream directly from the backend.

## Still open

- The desktop (`-tags desktop`) build embeds `frontend/dist`; it was not
  built here (no Wails toolchain on this machine).
- Consumers can be created and deleted but not edited.
- Saved credentials are still plain text in local storage; a "session only"
  option would be the next step.

## Stress test and design pass (2026-09-05)

### Load profile

`loadgen` publishes to 5 000 distinct subjects (6 levels deep, 200-byte JSON payloads) at 20 000 msg/s for 60 s against the dockerised NATS; the backend subscribes with `>`; one browser tab (headless Chrome, 1440×900) has the tree fully expanded, a leaf selected and types into the filter. Measured with a websocket meter (bytes per event type) and Chrome's Performance domain (long tasks, main-thread busy time, layouts, heap).

### Before

| Metric | Value |
|---|---|
| `subject-tree` traffic | 14.8 MB/s uncompressed, one 3.5 MB frame every 500 ms |
| `message-batch` traffic | 14.9 MB/s |
| Browser main thread busy | 62 % (32 long tasks, longest 348 ms) |
| Filter keystroke → rows updated | 224 ms |
| JS heap | 204 MB |
| Backend | 2 % CPU, 75 MB RSS |

Root causes: every tree node carried the complete last message (payload, headers, reply, subject repeated) and the whole nested tree was re-sent every 500 ms; the per-subject 10 msg/s throttle has no global cap, so 5 000 subjects × 4 msg/s all passed.

### Changes

- Tree feed is now a flat list of compact entries (`s, n, r, p, pt, ts, sz`) with the payload cut to 160 characters and no preview for binary payloads. The browser rebuilds the hierarchy (`buildTree`, one pass, one sort per level).
- After the initial snapshot (`full: true`) only subjects whose count or rate changed are sent; idle trees produce no frames. The emit interval backs off to 1 s above 2 000 subjects and 2 s above 10 000.
- Live feed budgets: focused subject/branch (sent by the browser as `focus`) up to 5 000 msg/s, everything else shares 1 000 msg/s with first-message-per-subject priority. The per-subject cap of 10 msg/s stays.
- Websocket permessage-deflate enabled (message batches shrink to ~6 % on the wire).
- Old timestamps are pruned while computing rates instead of only after 200 entries.

### After (same load)

| Metric | Before | After |
|---|---|---|
| `subject-tree` traffic | 14.8 MB/s | 1.4 MB/s uncompressed (1 frame/s), ~10 % on the wire |
| `message-batch` traffic | 14.9 MB/s | 0.37 MB/s |
| Main thread busy | 62 % | 11 % (16 long tasks, longest 112 ms) |
| Filter latency | 224 ms | 25 ms |
| JS heap | 204 MB | 50 MB |
| Backend | 2 % CPU / 75 MB | 5 % CPU (compression) / 41 MB |

### Design review (1440×900 and 1024×700, dark and light)

Reviewed every module with a seeded data set (orders stream with a consumer, KV bucket with history, object store, a micro service, live plant/fleet/alert traffic). Overall hierarchy, spacing, contrast and the light theme hold up at both sizes; the monitoring cards wrap cleanly at 1024 px and tables scroll inside their panes. Fixed:

- **Subject tree noise**: with a `>` subscription the tree opened with `_INBOX`, `$JS`, `$KV`, `$O` and `$SRV` roots above the real data. System roots are now hidden by default with an eye toggle in the pane header (persisted; a filter starting with `$` or `_` shows them regardless), and the empty state explains when only system traffic has been seen.
- **Stream list noise**: `KV_*`/`OBJ_*` backing streams dominated the list; they are hidden by default behind the same kind of toggle since Key-Value and Object Store have their own modules. "0 cons" became "0 consumers".
- **Branch view had no publish drawer**: "Publish here" on a branch opened nothing. The drawer is now shared by leaf and branch views and prefills `branch.` so the user completes the subject.
- **Pager label** "#59 – #108 of 1–108" became "59–108 of seq 1–108"; "1 revisions" pluralised; the tree's empty state distinguishes "Not connected" from "Waiting for messages".
- **e2e suite** now disconnects leftover backend connections before running so it is hermetic against a manual session.

Left as is (deliberately): duplicated "Connections" entry points (header button and switcher menu) are useful from both places; the object store has no per-object detail pane because there is nothing to show beyond the row.

## Visual tightening and perceived speed (2026-09-05, evening)

Goal: the UI should read like a tool, not like a generated dashboard.

- **Figures instead of tiles.** The card grids on stream overview, monitoring, server and service pages became a single strip of figures separated by hairlines (`StatStrip`/`StatTile`). Monitoring's JetStream and Subscriptions boxes are plain sections now.
- **Plain empty states.** No icon-in-a-circle; a short title and one line of explanation.
- **One heading style.** Pane titles are sentence case, section titles and table headers lost their uppercase/letter-spacing.
- **Quiet destructive actions.** Delete/Purge buttons sit neutral next to the other actions and only turn red on hover; the confirmation dialog keeps a solid red button.
- **Less chrome.** Success toasts removed everywhere (the UI already shows the result); the header lost the duplicate msg/s pill; the tree's rate bars became plain numbers, orange only above 10 msg/s; the chart's gradient fill became a flat tint.
- **Instant module switches.** `useAsync` keeps a keyed result cache: coming back to a list or detail renders the last data immediately and revalidates in the background, and refresh ticks no longer flash a spinner.

## Request templates and repeated runs (2026-09-05, late)

Asked for: reproducing many requests and saving request templates, Postman-style.

- `POST /api/run` repeats a publish or request server-side (count ≤ 10 000, concurrency ≤ 64, optional pause per sender, 120 s ceiling) and returns sent/ok/errors, throughput, latency min/avg/p50/p95/max, the first five replies and error samples grouped by message. `{{i}}`, `{{ts}}`, `{{uuid}}` and `{{rand:MIN-MAX}}` are expanded per message in subject, payload and header values. Covered by handler unit tests and the embedded-server e2e test (echo responder, and a run without responders).
- The publish drawer has a "Repeat ×" control that switches the send button to a run and shows the summary strip; "Parallel" and "Every … ms" appear for repeated runs.
- Templates live in the browser (`ne.requests.v1`): save as / save changes / delete from the Templates menu, export all as JSON and import a file (envelope or bare array, malformed entries dropped). A loaded template shows its name in the menu button and a dot when edited.

## JetStream domains (2026-09-06)

Asked for: reaching leaf-node JetStream through the hub cluster (and the other way round) as a connection parameter.

- Connection config gained `jsDomain` and `jsApiPrefix`; the backend builds its JetStream context with `NewWithDomain`/`NewWithAPIPrefix` for every stream, consumer, KV, object store and live-watch call, and for the account probe in the server view.
- Every JetStream route accepts `?domain=` as a per-call override; the websocket `kv-watch`/`stream-tail` commands carry `domain` too. The JetStream, KV and Object Store panes show a small domain control (globe icon) that switches the active connection to another domain without editing it; recent domains are offered as suggestions, the async cache is flushed and selections reset on switch.
- Embedded-server test runs with `JetStreamDomain: "hub"`: a connection with `jsDomain: hub` lists the same streams, an override to an unknown domain fails, and the account info reports the domain.

## Requests module, monitoring charts, TLS certificates (2026-09-06)

- **Requests module** (rail icon "Requests"): the template list is the explorer pane (new, import, export, filter), the editor is the detail pane (name, mode, subject, headers, payload, repeat settings, Save with Ctrl+S, Duplicate, Delete, run with result summary). The publish drawer under a subject reuses the same `RequestForm`/`useRequestRunner` and offers "Open Requests module". Works without a connection; sending needs one.
- **Monitoring**: every poll is recorded in an in-memory history per connection (an hour at 5 s). Six small charts show messages/s and bytes/s in vs out, JetStream API calls and errors per second, client connections and slow consumers, subscriptions and CPU. Cluster routes and leaf nodes (`/leafz`) get tables with RTT, subscriptions and in/out traffic.
- **TLS**: connection config carries `tlsCa`, `tlsCert`, `tlsKey` (PEM) and `tlsInsecure`; the backend builds a `tls.Config` (root pool, client key pair, min TLS 1.2) and rejects broken material with a clear error. The dialog shows the three PEM fields with "Load file…" when "Use TLS" is on. Unit-tested with generated certificates.

## Installable desktop app (2026-09-06)

Goal: install NATS Explorer like MQTT Explorer on Windows, macOS and Linux, built by the GitHub pipeline.

- The Wails desktop mode (`go-server/desktop.go`, `-tags desktop`) now has a `wails.json`, an app icon, Linux desktop entry, a macOS `Info.plist` (bundle id, local-networking exception for the embedded API) and the Wails-generated Windows resources (icon, manifest, NSIS script switched to a per-user install under `%LOCALAPPDATA%\Programs`). The window title carries the version stamped at build time.
- `scripts/build-desktop.sh linux|windows|macos` builds and packages exactly what the workflow ships: AppImage + .deb + tar.gz, NSIS setup + portable zip (Windows cross-compiled from Linux), universal .app + .dmg (ad-hoc signed). `--docker` runs the Linux/Windows variants in `scripts/desktop-builder.Dockerfile`, an image that mirrors the Ubuntu runner (Go 1.26, Wails 2.11, webkit2gtk 4.1, NSIS, appimagetool).
- `scripts/smoke-desktop.sh` starts a build (under Xvfb when headless), waits for the embedded API, checks `/api/auth`, the served UI and a websocket upgrade, and screenshots the window. `scripts/smoke-windows.ps1` installs the setup silently, launches the installed app, finds its API port, checks it, and uninstalls.
- `release.yml` was rewritten: one frontend build, three desktop jobs (Linux/Windows/macOS runners) each with its smoke test, headless server builds for five OS/arch pairs, Docker image, then a GitHub release with `SHA256SUMS.txt`. `workflow_dispatch` builds artifacts without publishing. `ci.yml` builds and smoke-tests the Linux desktop app on every push.
- Verified locally: Linux binary, AppImage (extract-and-run) and the .deb (installed into a fresh Ubuntu 24.04 with runtime deps only, launched, removed) all pass the smoke test; the binary also starts on this Ubuntu desktop against the system webkit; the Windows exe and NSIS installer build in the container (`PE32 … Nullsoft Installer`). macOS packaging could not be run here and relies on the macOS runner job.
- Limits: no code signing or notarization (needs Apple/Windows certificates as repository secrets); documented in the README install table. Linux needs webkit2gtk 4.1 (Ubuntu 22.04+, Debian 12+, Fedora 37+).

## Persistent settings for the desktop app (2026-09-06)

Found while checking the packaged app: the desktop window loads `http://127.0.0.1:<random port>`, so the browser-style localStorage changed its origin on every start and connections and templates were lost between launches.

- New `internal/settings` store: `settings.json` in `os.UserConfigDir()/nats-explorer` (0700/0600), entries keyed like the browser (`ne.*`), written atomically. Connection credentials (`token`, `pass`, `nkeySeed`, `creds`, `tlsKey`) are split off into the OS keyring (probe on start; `NO_KEYRING=1` or no keyring → `secrets.json`, 0600) and merged back on read; stale secrets are removed when a connection disappears.
- API: `GET /api/app` (mode, storage, secrets backend, config dir, version), `GET /api/settings`, `PUT/DELETE /api/settings/{key}` (only `ne.*` keys, JSON values, 4 MB cap). Enabled in the desktop build and in the server with `STORAGE_DIR`.
- UI: `lib/storage.ts` hydrates localStorage from the backend before the first render and funnels every write (`persist`) to localStorage plus a debounced PUT; all writers (connections, templates, theme, chart type, hidden subjects/streams, explorer width, recent sends, recent domains) go through it. If a token is required, hydration retries after login and the stores are re-read. The connection dialog explains where data and secrets live.
- Tests: settings store (secret split/merge, stale-secret cleanup, invalid keys, file permissions, fallback), server API test with a temp store, storage helper unit tests; the desktop smoke test now writes a setting, restarts the app and expects it back.
- Follow-up found by the e2e suite: with the UI now loading after hydration, the "Not connected" screen flashed before the websocket had reported existing backend connections (and Playwright's click landed on a vanishing button). `Detail` renders nothing until the first connection list arrived (`connectionsLoaded`).

## Cluster module (2026-09-06)

- Connections take optional system-account credentials (`sysAuthMethod`, token / user+pass / nkey / creds; stored like the other secrets). The backend opens a second NATS connection with them; failures are reported in the connection status, never fatal.
- `GET /api/cluster/{connId}/overview` fans out `$SYS.REQ.SERVER.PING.STATSZ` and `.JSZ` (accounts, streams, config) over that connection and collects replies until the servers go quiet (300 ms, 2 s cap): every server with CPU, memory, connections, subscriptions, traffic, routes and JetStream usage, the meta cluster with leader and peer state, and every stream with storage, replica count, leader and per-peer current/lag/offline. Without system credentials it falls back to the connected node's monitoring endpoint and says so.
- UI: the "Server" module became "Cluster" with two tabs: the overview (status strip, server table with the meta leader marked, meta cluster peers, stream placement with colour-coded peers) and the per-connection cards from before. A "System account…" button leads to the connection dialog when the view is single-server.
- Verified against the local three-node hub with system account plus the leaf sharing `$SYS`: four servers answer, the meta leader is marked, streams show leader and replicas; the embedded-server test covers fallback, system-account success and wrong system credentials.
- Side fix: the inline theme script in `index.html` still read the bare `dark`/`light` word; since settings sync stores JSON it now parses the quoted value (a fresh profile fell back to the system theme before).
